# Product Concept

See [Product Roadmap](roadmap.md) for the confirmed first-release scope and implementation phases.

## Product Vision

A mobile-first personal health and fitness tracking service that turns a user's health records into useful feedback and a positive, game-like growth experience. The product supports consistent behavior and visible progress; missed days do not erase accumulated progress.

## Initial Release Scope

- The first release is a private, single-user personal app. In-app registration and multi-user support are out of scope initially.
- Include all planned core domains, the Avatar/XP progression loop, progress views, and AI features in the first complete release; AI is not deferred to a later product milestone.
- UI access still needs protection if the app is remotely reachable. The access-control implementation is not yet finalized.
- The initial AI integration uses Pi on the development Mac through the local bridge and Cloudflare Tunnel. AI availability therefore depends on that Mac and its connection being online.
- Roadmap phases describe implementation order, not a reduced feature scope for the first release.

## User Confirmation Principle

The app may offer recommendations, inferred values, and prefilled suggestions, but the user makes the decisions and confirms records across every domain. Suggestions—including extracted `Food Items`, workout actions, meal recommendations, and body-metric values—remain proposals and must not create or modify user source records, be applied to a `Plan`/`Goal`, or be treated as completed behavior until the user explicitly confirms. Derived AI outputs and recommendation sessions may be stored separately as specified, but are not user-confirmed facts. A deliberate Save, Confirm, or Continue action counts as confirmation; do not add a redundant confirmation dialog. Derived analysis may be shown after its source record is confirmed and saved.

## Core Domains

- **Meals**: record meal photos, `Food Items`, `Place`, dining companions, and time. Provide separate `Meal Photo`, `Receipt/Order Import`, and `Manual Food Item Entry` paths. AI extracts candidate `Food Items` from meal photos and image-based receipts/orders, recognizing a specific brand/menu item when possible or a generic food item otherwise. The user reviews and confirms, edits, removes, or adds items before saving. Retain the original receipt/order image with the saved Meal. Deleting a Meal deletes all images associated with it, including meal photos and retained receipt/order images. Receipt/order PDF import is not supported initially. After a meal is recorded, AI shows nutrition analysis such as `Calories`, carbohydrates, protein, fat, sugar, and sodium, then ends the meal flow without unsolicited improvement advice. For a filled `Meal Slot`, provide `View`, `Edit`, and `Delete` buttons. `View` opens the saved Meal's `Meal Detail` page and analysis; `Edit` changes the saved Meal through the normal review-and-confirm flow; `Delete` opens the same `Delete`/`Cancel` modal used in `Meal List` without navigating. `Cancel` closes the modal and leaves the Meal unchanged; `Delete` removes the Meal and its associated images, leaving the slot empty. Post-breakfast, Post-lunch, and Post-dinner open their corresponding `Meal Slot` directly. Recommendation, logging/analysis, Edit, and Delete flows from these touchpoints return Home when finished. `View` opens `Meal Detail`; its back action always returns to `Meal List`, regardless of entry point. Users can explicitly request on-demand meal/menu recommendations based on prior meals, current body metrics, active goals, current time, and remaining meal slots. Include a navigation-list entry to a dedicated `Meal List` page for reviewing saved Meals. Each list item links to its `Meal Detail` page and has per-item `Edit` and `Delete` buttons. `Meal Detail` back navigation returns to `Meal List`. When Edit is launched from `Meal List`, saving or going back returns to `Meal List`. Delete opens a `Delete`/`Cancel` modal without navigating; either choice leaves the user on `Meal List`.
- **Supplements**: record supplement items, dosage, and intake time. Items taken together may be grouped in one `Supplement Intake`; confirm each item's taken status and dosage independently. Support daily and weekly goals and routine adherence.
- **Workouts**: classify a workout as `Strength Training`, `Cardio/Endurance`, `Sport`, `Mobility/Recovery`, or `Other`, using the relevant logging form for each type. Within `Strength Training`, distinguish `Machine`, `Free Weight`, and `Bodyweight` modes; these are not top-level workout types. Provide a curated button list without search: `Machine`—`Chest Press`, `Lat Pulldown`, `Seated Cable Row`, `Shoulder Press`, `Leg Press`, `Leg Extension`, `Leg Curl`, `Chest Fly`, `Triceps Pushdown`, `Biceps Curl`; `Free Weight`—`Barbell Bench Press`, `Dumbbell Bench Press`, `Barbell Squat`, `Deadlift`, `Romanian Deadlift`, `Overhead Press`, `Barbell Row`, `Dumbbell Row`, `Dumbbell Lateral Raise`, `Dumbbell Curl`; `Bodyweight`—`Push-up`, `Pull-up`, `Chin-up`, `Dip`, `Bodyweight Squat`, `Lunge`, `Glute Bridge`, `Calf Raise`, `Sit-up`. Initial primary-muscle defaults for every curated exercise are in [Strength Exercise: Default Target Muscles](strength-exercise-muscle-defaults.md). Use direct input for items not in the curated list. Record applicable exercises, sets, duration, distance, place, and an optional workout-level `Note`. `Note` is plain text entered in a textarea, with no Markdown; when left blank, store an empty string. For `Sport`, offer common choices—`Soccer/Futsal`, `Basketball`, `Volleyball`, `Baseball`, `Tennis`, `Badminton`, `Table Tennis`, `Golf`, and `Combat Sports`—plus `Other Sport` with a user-entered name. For `Cardio/Endurance`, offer `Running`, `Walking`, `Cycling`, `Swimming`, `Rowing`, `Elliptical`, `Stair Climber`, `Hiking`, and `Jump Rope`. For `Strength Training`, store `Reps` and a single optional `Load` field separately for each set; do not record rest time. For a bodyweight-only set, leave `Load` empty rather than entering zero or the user's `Body Weight`. For `Cardio/Endurance`, use recorded `Duration` and `Distance` to derive `Pace` in min/km when both are available; do not treat the calculated `Pace` as a separately entered source value. A `Workout` contains an ordered list of `Workout Items` that the user can reorder and edit individually. A `+` between items opens a vertical button-list picker and inserts one selected item at that position; add items one at a time with no separate batch mode. Do not provide search; use curated options and the direct-input modal for items not listed. Give picker buttons generous horizontal and vertical spacing and use vertical scrolling. Show a subtle top fade when the list is scrolled below its start and a subtle bottom fade when more items continue below the viewport. The picker also offers direct input in a modal with recent custom items shown newest-first as buttons. Selecting a recent item inserts it at the current position. After the same custom item string has been added three times—including additions via a recent-item button—promote it to the regular options in that picker. Count items only when their strings are exactly identical; do not normalize whitespace, case, or other characters. For `Strength Training`, each item is an exercise with nested sets. The same list can be edited during or after the activity. `Post-workout` is an entry point for recording or editing the workout, not a summary or recap screen. For `Mobility/Recovery`, choose `Stretching`, `Yoga`, `Mobility Drill`, `Foam Rolling`, or `Other` with a user-entered name. Record `Duration`, with optional `Target Muscle Groups`, `Place`, and `Note`; do not record `Reps`, `Load`, or `Distance`. For the `Other` workout type, require a user-entered activity name and `Duration`, with optional `Place` and `Note`. A `Program` may define a split such as two- or three-day training. Use past records and the program to suggest the next workout and exercise prescription. When logging from today's `Plan`, link the `Workout` to that `Plan` item and load the scheduled workout and its planned items as an editable draft in the type-specific workout flow; the user enters actual performance values, and planned values are not treated as actual results. Saving the `Workout` creates its source record but does not complete the linked `Plan` item; the user marks that item complete through a separate explicit action. Provide explicit completion actions on the `Plan` list and `Plan` item detail. After saving a `Workout`, if incomplete `Plan Items` remain in today's `Plan`, show a dedicated `Plan` completion screen listing them all. Each item has an individual completion action; complete one item per action, with no multi-select or bulk completion. Completing an item updates it in place and keeps the user on this screen so they may complete other items. A `완료` button exits the screen and continues the flow. This is a `Plan` completion screen, not a `Workout` recap. Do not model partial completion as a separate `Plan` status; the user decides explicitly whether the item is complete. A `Workout` started from the general workout entry point is saved unlinked. After the post-Workout `Plan` completion step (if shown), an unlinked `Workout` proceeds to a separate optional `Plan` selection step listing today's workout `Plan Items`. The user may select one item; pressing `완료` links it, while pressing `완료` with no selection skips linking and leaves the `Workout` unlinked. Linking does not complete the `Plan Item`, and no link is inferred or auto-matched. After the post-Workout completion/link flow ends, return to Home regardless of the Workout's entry point.
- **Body Metrics**: record height, body weight, and individual body-composition measurements. To correct an incorrect saved measurement, undo the most recent measurement for that metric and enter the correct value as a new measurement; do not provide a separate edit action for saved measurements. After an undo, the preceding measurement does not become undoable; only a newly confirmed measurement for that metric can subsequently be undone. Undo removes the measurement record and its XP award entirely, as if they had never existed; do not retain an audit record for the undone measurement or its award. Recalculate affected XP and level history without that award, including past graph values, rather than showing a reversal on the undo date. Exclude the undone measurement from comparisons and apply the existing 7-day rule to remaining records; a re-entered value is evaluated normally. Displayed levels are recalculated from XP and may decrease if undo cancels an award. An InBody assessment is a measurement event/source, not a single metric; store its resulting metrics separately. Support manual entry of InBody values and report-image upload with AI extraction; the user reviews and confirms or corrects extracted metrics before saving. These are the only InBody entry paths in the initial release; direct CSV import is unsupported. Do not retain the uploaded report image: delete the temporary image when the extraction/review flow ends, and keep only user-confirmed metrics. Use the supplied [InBody Report Field Reference](inbody-csv-fields.md) as the supported field set: the report image is authoritative, fields present only in the CSV are excluded, and only the current assessment is saved (not points read from the history chart).
- **Goals**: the initial Goal setup offers four types—`Target Body Weight`, `Target Body Fat Percentage`, `Muscle Gain`, and `Performance Goal`—each with a `Target Date`. `Target Body Weight` stores only the target weight and date; `Target Body Fat Percentage` stores only the target percentage and date. Neither stores a separate start value. `Muscle Gain` has two sub-options: general muscle development with a `Target Date` but no numeric target, or whole-body InBody `Skeletal Muscle Mass` with a target value and `Target Date`. The InBody option is a subtype of `Muscle Gain`, not an additional top-level Goal Type. `Performance Goal` stores one or more target performance metrics and values with units, plus a `Target Date`; it does not store a separate start value. A goal may combine metrics, such as a target distance and duration for a run; a combined goal is achieved only when all target conditions are met. Workout records provide observed progress. Default achievement directions are `Load`, `Reps`, `Distance`, and hold `Duration` at or above target; completion `Duration` and `Pace` at or below target. Thus `Duration` direction depends on the activity (for example, plank hold vs. 5km completion time). Support all discussed metric families: `Load`, `Reps`, `Distance`, `Duration`/time, and `Pace`. Use metric defaults: `Load` in kg, `Distance` in km, `Duration` in seconds or minutes as appropriate, `Reps` as a count, and `Pace` in min/km. Additional units can be added later if needed.
- **Progress Photos**: let users upload dated photos and review them chronologically or side by side.

## Data Layers

Keep these concepts distinct throughout domain models, storage, and application code:

1. **User-Generated Data / Source Data** — information the user enters or uploads, including photos and measurements from a device.
2. **Derived Data** — values calculated or inferred from source records, including AI nutrition estimates, workout metrics, adherence, trends, recommendations, XP, and levels. AI outputs are estimates, not user-entered facts.
3. **Presentation Model** — data composed for a particular screen. It may combine source and derived data and does not have to be stored as a separate canonical record.

## Units and Timezone

Store unit-bearing values in canonical metric units and convert them for display using one profile-wide `Metric` or `Imperial` preference. Default to `Metric`. Support `kg`/`lb` for mass, `cm`/`in` for height, `km`/`mi` for distance, and `min/km`/`min/mi` for pace; counts, durations, ratios, and other unitless values are not converted. The profile timezone defaults to the device timezone and can be changed by the user. Store each event's UTC instant and timezone at recording; use that timezone for its local-day and daily XP assignment. A profile timezone change affects future events only and does not reassign historical days.

## Gamification

- The **Avatar** is the central growth visualization on the home screen.
- Track separate levels for muscle groups and body-related metrics, plus an overall character level. Avatar XP is the sum of XP awarded across body metrics, muscle groups, supplements, and other areas; count each area award once. Canceling an award also removes it from the Avatar total. Award 1 muscle XP per target muscle group once per qualifying exercise item in a Workout, not once per Workout or set. When an exercise targets multiple muscle groups, grant 1 XP to each target group rather than splitting it; each group award contributes separately to the Avatar total. Within Strength Training, a `Machine` or `Free Weight` exercise item qualifies once its confirmed saved Workout contains at least one set with 1 or more recorded reps; Load is optional. `Bodyweight` items do not award muscle XP, even when a Load is recorded. Planned items without actual performance values do not qualify. For a curated Strength Training exercise with no previously saved user selection, prefill only its primary muscle group or groups, excluding secondary and stabilizing muscles. On reuse, prefill the target groups from the most recently confirmed and saved instance of that curated exercise, including an empty selection; the user may change them before confirming the Workout. User selections do not modify the curated catalog's default mapping. For a custom exercise, prefill the target muscle groups from the most recently confirmed and saved matching custom exercise in the same picker; matching uses the exact name without normalization. The user may change them, and no matching saved record means an empty selection. Target groups are optional: a Workout may be saved without them, but an exercise with no target groups awards no muscle XP. The initial muscle groups are `Chest`, `Back`, `Shoulders`, `Biceps`, `Triceps`, `Core`, `Glutes`, `Quadriceps`, `Hamstrings`, and `Calves`. Repeated entries of the same exercise in one Workout each qualify independently and award XP per target group. When a saved Workout is edited and confirmed, recalculate its muscle XP from its current qualifying items and target groups: cancel awards that no longer qualify and grant newly qualifying awards, without duplicate awards for unchanged item/group pairs. The Avatar total and displayed levels follow the resulting XP. Show XP and level changes from a Workout edit on the date of that edit; do not rewrite earlier dates, which retain the values shown before the correction. Only qualifying `Machine` and `Free Weight` strength exercises award direct exercise XP. `Bodyweight`, `Cardio/Endurance`, `Sport`, `Mobility/Recovery`, and `Other` exercise records award no direct muscle or other exercise XP initially. The [exercise default muscle mappings](strength-exercise-muscle-defaults.md) provide the initial catalog values.
- All levels start at Level 1. Derive displayed levels from their XP rather than storing an independent level.
- Reward defined positive behaviors with XP. Never subtract XP for missed records, inactivity, or an unfavorable result.
- Use the same fixed threshold of 10 XP per level for body metrics, muscle groups, and the Avatar. Level is `1 + floor(XP / 10)`; it does not require more XP per level at higher levels.
- Award supplement XP by completion of planned supplement intake occurrences: below 50% earns 0 XP, 50% to below 100% earns 1 XP, and 100% earns 2 XP. Each scheduled per-item intake occurrence counts once when confirmed as taken; if the same supplement is scheduled more than once, each occurrence counts separately. Record actual dosage separately; it does not multiply the XP unit. Calculate this percentage per day using the user's configured timezone.
- Provide a separate progression view with XP and level history so users can recognize periods of growth and plateaus.

For a body-metric level tied to a numeric `Goal`, award 1 XP for that metric on a local day when the absolute gap between its latest confirmed value and the `Goal` target decreases by any amount; an unchanged gap does not qualify. Compare stored canonical metric values without display rounding, and do not award XP for numeric conversion or floating-point artifacts. Award at most 1 XP per metric per local calendar date, immediately on the first qualifying confirmed measurement; later measurements with the same recording-time local date do not award additional XP, even if recorded in a different timezone. Unless a Goal is edited or newly activated, later measurements do not replace that XP-awarded measurement as the 7-day XP comparison baseline; if there is no eligible XP measurement in that window, use the previous confirmed measurement as usual. This is not based on a universal increase/decrease direction. Undoing a measurement cancels the XP it awarded; displayed levels are recalculated from XP and may decrease. Allow at most one active numeric `Goal` per body metric. Inactive Goals may remain as history; the active Goal determines XP regardless of whether it is the `Primary Goal`. There is no separate Goal selection for XP. Compare with the most recent prior measurement that earned XP for the metric on the current local date or any of the preceding seven local dates (up to eight calendar dates, using each event's recording-time local date); if none exists, compare with the previous eligible confirmed measurement, excluding measurements before the current Goal was activated or edited. If no previous confirmed measurement exists, award 1 XP for the first confirmed measurement as a recording reward and use that measurement as the comparison baseline. Do not store a fabricated initial value. When a Goal is newly activated or the active Goal's contents are edited, reset its XP comparison history: ignore earlier measurements when evaluating that Goal, while retaining those measurements and previously awarded XP as history. The first confirmed measurement afterward is eligible for 1 XP as a new-start reward and establishes the new comparison baseline; the per-metric daily 1 XP limit still applies. If that measurement is undone and no eligible measurement remains since the reset, treat the next confirmed measurement as the first again; cancel only XP awarded by the undone measurement and retain any other daily award. A Goal without a numeric target does not grant separate Goal XP or body-metric XP based on target-gap progress. Activity XP follows its own rules.

## Daily Touchpoints

The user journey is divided into six contextual touchpoints rather than one generic daily check-in:

1. **Wake-up** — after waking.
2. **Post-breakfast** — after breakfast.
3. **Post-lunch** — after lunch.
4. **Post-dinner** — after dinner.
5. **Post-workout** — after a workout.
6. **Bedtime** — before sleep.

These are flexible entry points, not mandatory steps or a strict clock-based sequence. Users may skip irrelevant touchpoints without penalty; undoing a body-metric measurement cancels XP awarded by that measurement. `Bedtime` is a lightweight end-of-day closeout for reviewing today's `Plan` and recorded activity; it does not add a Sleep domain or bedtime/wake-time logging. The screen may use the existing individual `Plan Item` completion action for remaining items; do not add bulk or automatic completion. Do not send Bedtime reminders.

The daily `Plan` is assembled from existing schedules, including workouts from `Program` and scheduled supplement routines. Users can manually add other actions; a separate full-featured planner is not required for the initial release. Start workout logging directly from today's `Plan` or the workout logging entry point; there is no standalone `Pre-workout` page or pre-workout-only data collection. Users can view or change today's scheduled workout in `Plan`; changing today's `Plan` does not change the recurring `Program` schedule unless the user separately edits `Program`.

Post-breakfast, Post-lunch, and Post-dinner each open today's corresponding `Meal Slot` directly. Meal logging ends after showing AI nutrition analysis. Meal/menu recommendations are user-initiated, not automatically suggested after logging. Tapping an empty `Meal Slot` opens a modal `Action Sheet` with two choices: `Menu Recommendation` or `Log Meal`. `Log Meal` then offers separate `Meal Photo`, `Receipt/Order Import`, and `Manual Food Item Entry` paths. Receipt/order extraction is a reviewable candidate list; only user-confirmed items are saved.

`Menu Recommendation` opens a separate page that returns 1–3 ranked menu options with reasons, using prior meal records, current body metrics, active goals, current time, and remaining meal slots. It does not create or change a Meal, `Draft`, or `Plan`. On leaving the page, store a `Menu Recommendation Session`—the internal record of this one use—containing request/end timestamps, the relevant `Meal Slot`, the exact structured input sent to AI, the 1–3 ranked menu options and reasons shown, the selected rank or no selection, and AI provider/model ID and prompt version. Retain each session indefinitely with no automatic expiry and use it to inform future recommendations. Store the structured input snapshot, not duplicate original photo files.

### Wake-up Flow

The Wake-up experience is a sequence of focused pages:

1. Show the current `Body Weight` as an editable input for a new measurement, not an edit of an existing saved measurement. Do not ask for or display `Height` here; height changes infrequently and remains available in Body Metrics.
2. Show a daily-granularity `Body Weight` graph covering the past 14 days. Use the same visual chart design as the XP graph, with scale/reference intervals of 5 display units (5 kg when the selected unit is kg).
3. Show the current `Avatar` level and XP.
4. Show a daily-granularity 14-day progression graph with a cumulative XP line and an `Avatar` Level step line.
5. If a `Primary Goal` exists and today's `Plan` has at least one incomplete, feasible item, show exactly one `Next Best Action` for something to do at any point during the current day. Balance today's `Plan` with progress toward the `Primary Goal`; the action does not have to start immediately.
6. If no eligible item exists in today's `Plan`, skip the `Next Best Action` page and finish the Wake-up flow.
7. If no `Primary Goal` exists, show the four Goal setup choices instead. If no choices are available to present, show only today's `Plan` and finish the Wake-up flow.

If the user leaves `Body Weight` unchanged and continues, record that day's entry using the saved value; pressing Continue is explicit confirmation, so a separate skip action or redundant confirmation dialog is not required. This provides a value for the day when the entry is confirmed; an undone entry no longer appears in the 14-day graph. The two graphs share the same visual design and differ in their plotted values and scale.

Users can designate one active `Goal` as their `Primary Goal`. When a `Primary Goal` exists, `Next Best Action` uses a **Balanced, discomfort-avoiding** policy to rank only incomplete, feasible actions already in today's `Plan`. Progress toward the `Primary Goal` informs ranking but does not add actions from outside the `Plan`; AI must not invent or generate actions. Among eligible items, favor lower-disruption options. When candidates are otherwise similarly suitable, break ties in this order: lower disruption; earlier scheduled time when available; then earlier position in today's displayed `Plan` order. Use only known Plan/action information; do not invent missing schedule or disruption details. The aim is to avoid unpleasant recommendations, not maximize user satisfaction. `Not now` is the only explicit decline; there is no `Don't suggest again` control. No response or leaving the recommendation is neutral and creates no feedback event. Record explicit feedback as `Next Best Action Feedback` with occurrence time, source `Plan` item ID, original recommended `Plan` item snapshot, and interaction type (`execution_opened` or `not_now`). Edits after navigating belong to the destination flow's feedback, not `Next Best Action Feedback`. Do not ask the user to provide a reason. Within a rolling 30-day lookback window, count explicit `Not now` skips among similar recommendations; the first three do not lower priority, and the fourth and subsequent instances add a soft negative signal. Do not include edits made after navigating to the destination page in `Next Best Action` feedback. Let AI determine which recent recommendations are similar rather than maintaining a fixed action taxonomy. For AI ranking, provide a compact structured snapshot rather than a prose summary or the user's full history: the `Primary Goal` type, structured target(s) and `Target Date` where applicable, and latest relevant confirmed progress value(s); each eligible `Plan` item's ID, action/type, scheduled time when available, displayed `Plan` order, and incomplete status; and only explicit `Not now` feedback from the rolling 30-day window, with its original recommended `Plan` item snapshot. Record `execution_opened` as a page interaction, but exclude it from AI ranking inputs; it neither raises nor lowers priority and never counts as completion. AI compares candidates' fit to today's `Plan`, progress toward the `Primary Goal`, recent `Not now` feedback, and likely disruption. Do not assign the negative signal a fixed numeric penalty. The AI output contains the selected existing `Plan` item ID and a reason string. Do not show the reason or copy/display/prefill `Plan` values in the UI. If an execution page exists, show a link button for the selected action and navigate to it. If no execution page exists, show only the `Next Best Action` and finish the Wake-up flow with no button. The AI must not return a URL or new action. The recommendation itself does not change a source record or `Plan`; any action on the destination page follows its normal confirmation behavior. Deterministic rules may remove completed or infeasible candidates before AI ranks the remainder. Do not give AI the user's full history.

## UX and Visual Direction

- **Mobile-first**, with little information on each screen.
- Split tasks into focused screens rather than creating a dense all-in-one dashboard.
- Use progressive disclosure for details and analysis.
- Use a minimalist visual language based primarily on dots and lines, with minimal filled surfaces.
- The home screen centers on the Avatar and concise growth information; detailed logging, analysis, goals, photos, and progression live in focused views.
- UI copy is Korean. Canonical domain terms, code identifiers, and engineering discussions use English.

## Initial Technology Direction

- **Runtime and data**: Cloudflare Workers, D1, and R2.
- **Web application**: pnpm, TanStack Start, and shadcn/ui.
- **Client libraries**: TanStack Form for forms, TanStack Query for remote/server state, and Zustand for client-only state.
- Define clear ownership between route loaders and TanStack Query to avoid maintaining duplicate server-state caches.
- **AI prototype**: connect to Pi running on the development Mac through Pi CLI RPC mode and a local HTTP bridge. See [Cloudflare CLI and Pi Bridge](cloudflare-cli.md).

Additional dependencies such as schema validation, an ORM, or charting libraries have not been selected yet.
