# 2026-11-12 작업 기록

## 1. 기본 운동별 주 대상 근육

사용자의 위임에 따라 기본 Strength Training 운동 29개의 주 대상 근육을 [Strength Exercise: Default Target Muscles](../docs/strength-exercise-muscle-defaults.md)에 정리했다. Machine·Free Weight뿐 아니라 기록용 Bodyweight 운동도 포함한다. 주 대상이 복수인 종목은 여러 부위를 두되 보조·안정화 부위는 제외했다. 이전에 저장한 사용자 선택은 catalog 기본값보다 우선하고, Bodyweight는 대상 근육이 있어도 XP를 주지 않는다.

## 2. MVP 개발 중 접근과 AI 운영

실제 건강 데이터와 로컬 Pi agent를 사용한다. MVP 완성 직전까지 앱 접근 관리를 미루고 배포 앱은 로그인 없이 공개하며, 그전에는 DB와 API에 소유자를 모델링하지 않는다. 이 기간에는 공개 방문자의 데이터 조회·변경·삭제 및 노출된 AI 기능 사용이 가능하다. Worker와 로컬 bridge 사이의 Access 보호는 앱 사용자 접근 관리와 별도로 유지한다. 로컬 Pi의 모델 제공자가 외부일 수 있으므로 실제 데이터를 AI에 보내기 전에 설정을 확인한다.

상세 문서: [Product Concept](../docs/product-concept.md), [Product Roadmap](../docs/roadmap.md), [Cloudflare CLI and Local Pi Bridge](../docs/cloudflare-cli.md)

## 3. Pi 모델 선택

사용자가 로컬 Pi agent의 모델로 `GPT-6 Luna XHigh`를 지정했다. Pi에 등록된 값은 provider `openai-codex`, model ID `gpt-6-luna`, thinking `xhigh`이며, 건강 정보가 없는 직접 CLI 요청이 성공했다. Pi 기본 모델은 `gpt-6.1-terra`이므로 bridge에서 모델을 명시해야 한다. Pi는 로컬에서 실행되지만 추론 요청은 OpenAI Codex 제공자로 전송된다. Worker와 bridge를 거치는 연결은 아직 검증하지 않았다.

## 4. Pi 워커 4개로 첫 실행 가능한 구현

사용자 요청대로 Orca 감독 아래 Pi `openai-codex/gpt-6-luna`, thinking `xhigh` 워커 4개를 실행했다. 현재 Orca의 Pi launch-time `--model` 옵션은 거부되어, 모델과 thinking을 명시한 Pi 터미널을 만든 뒤 감독 Task에 연결했다. 같은 checkout에서 앱·도메인·D1·브리지의 파일 소유 범위를 분리했고 커밋·원격 배포는 하지 않았다.

- 앱: TanStack Start/React, Query 단일 서버 상태 캐시, Form, Cloudflare Vite 기반을 만들고 한국어 몸무게 기록·숫자 목표·단위/시간대 설정과 최근 저장 측정 1회 되돌리기를 연결했다. 모든 도메인을 한 번에 만들기보다 첫 수동 기록 경로를 실제 D1에 연결하는 데 집중했다.
- 데이터: `migrations/0001_health_foundation.sql`, `src/server/health-api.ts`에 singleton 프로필, 세 가지 신체 지표 측정·숫자 목표 API를 구현했다. owner/auth나 가짜 건강 데이터는 넣지 않았다. 되돌리기는 실제 삭제이며 이전 기록의 되돌리기 권한을 복원하지 않는다.
- progression: `src/domain/`에 목표 격차·일일 제한·7일 비교 기준·reset·undo, 영양제 XP, 레벨·단위 변환, 운동별 대상 근육과 award reconciliation 순수 함수를 구현했다. XP의 D1 저장·화면 연결·과거 그래프는 아직 구현하지 않았다.
- 브리지: `bridge/`와 `src/ai/`에 독립 bearer 인증, 고정 smoke 요청, tools/MCP/extensions/context 비활성화, 큐·출력·시간 제한과 subprocess 종료 처리를 만들었다. 임의 prompt나 raw RPC는 노출하지 않는다.

리뷰에서 동일 timestamp의 일일 XP 중복, catalog의 상속된 속성 이름 처리, 새 브라우저에서 저장된 UTC 설정 덮어쓰기, 과거 날짜로 저장한 기록의 undo 버튼 누락, 단위 변경 시 입력 중인 숫자의 재해석을 발견해 회귀 테스트와 함께 수정했다. 브리지는 외부 timeout을 내부 제한보다 길게 맞추고, 종료가 확인될 때까지 동시 실행 슬롯을 유지하도록 보완했다.

## 6. 신체 지표 XP 저장과 14일 진행 화면 연결

사용자의 진행 요청에 따라 같은 Pi `gpt-6-luna/xhigh` 워커 3개를 데이터·집계/그래프·앱 연결에 재배정했다. `0002_body_metric_xp.sql`에 측정별 1 XP와 지표/기록 시점 localDate별 일일 제한을 저장하고, 기존 순수 지급 규칙을 실제 저장·undo에 연결했다. 목표 변경은 비교 기준만 초기화하고 과거 지급은 보존한다. undo는 측정과 그 지급만 삭제하며 되돌림 이력이나 이전 기록의 undo 권한을 만들지 않는다. 기존 측정에 소급 XP를 생성하지 않는다.

D1에는 interactive transaction이 없으므로 읽은 기준값을 그대로 쓰는 방식 대신 revision과 고유 write token으로 모든 후속 SQL을 보호하는 원자적 batch를 사용했다. 동시 저장·목표 변경·undo 충돌 시 최신 상태로 다시 평가하며, 반복 충돌은 409로 반환한다. 리뷰 중 목표 변경 interleaving 회귀 테스트 실패를 발견해 데이터 워커가 수정했다.

`GET /api/health/progression`은 저장된 이벤트 localDate로 정확히 14일을 구성한다. 체중이 없는 날은 null이며 일별 최신 기록만 표시하고, XP는 표시 구간 이전 지급도 포함해 누적한다. Avatar와 지표별 레벨은 XP에서 유도한다. 현재 화면은 신체 지표 지급만 반영한다고 명시하고, 운동·영양제 지급은 해당 source flow가 생길 때 연결한다.

체중·XP·Level SVG 그래프와 날짜별 접근성 표를 추가했다. 레벨 축을 임의 XP 눈금에 붙이면 계단선과 위치가 어긋나는 문제를 발견해 `(level - 1) × 10` 위치의 별도 눈금으로 수정했다. 체중은 kg/lb 표시 단위로 5단위 기준선을 유지하며 비정상적으로 큰 범위의 bounded fallback은 화면에서 알린다. 저장·undo·설정 변경 시 Query cache를 갱신하고, 날짜/시간대별 key와 자정 갱신으로 그래프 구간이 오래된 날짜에 머물지 않게 했다.

## 9. Strength Workout create 재시도 idempotency

`POST /api/health/workouts`는 UUID `Idempotency-Key`를 필수로 받고, 검증·정규화된 draft의 SHA-256 fingerprint와 workout ID만 보존한다. 같은 key와 같은 canonical draft는 이미 저장된 workout을 반환하고 award/event를 다시 쓰지 않으며, 같은 key에 다른 draft를 보내면 409, 삭제 후 replay는 410으로 끝난다. draft JSON과 API body는 바꾸지 않았다. UI는 폼 인스턴스당 한 action key를 만들어 오류 후 재시도에도 유지한다.

key mapping은 source·award·signed event 및 progression revision CAS와 동일한 D1 batch에 넣었다. 그래서 저장 중 실패하면 mapping만 남거나 XP가 중복 지급될 수 없다. 삭제 때 mapping은 남기되 source를 참조하는 FK는 두지 않아, 이름·세트 보존 없이도 삭제된 workout이 다시 생기지 않는다. migration-backed 테스트에서 같은 key의 동시 저장, canonical replay, payload mismatch, 삭제 tombstone, CAS/batch rollback을 확인했다.

검증: `pnpm test` 149/149, `pnpm typecheck`, `pnpm build`, `cf build`; `0001`–`0003`은 임시 persist 경로에만 적용했다. 기존 `.wrangler/state`와 원격 리소스는 건드리지 않았다.

## 10. 한 기능 한 페이지와 근력 운동 통합 검증 완료

홈을 이동 목록으로 바꾸고 몸무게 등록·목록·목표 조회·목표 등록·체중 변화·성장 기록·설정을 각각 분리했다. 운동도 목록·등록·상세·수정을 별도 route로 나눴다. TanStack 중첩 route에서 부모 목록/상세가 자식 편집 화면과 겹치지 않도록 부모는 Outlet-only layout, 실제 조회는 index route로 옮겼다. 인용된 안내문·FormField hint API·설명용 placeholder·footer 안내를 제거했으며 필수 레이블·단위·오류·접근성은 유지했다.

근력 운동의 순서형 picker·실제 reps/선택 Load·정확한 custom 이름과 최근 항목/3회 승격·이전 근육 선택 재사용·명시적 저장/수정/삭제를 연결했다. 합성 데이터 브라우저 검증에서 Nov 11의 과거 XP 5는 유지하면서 Nov 12 수정 후 XP 7, 삭제 후 Body Metric만 남은 XP 1로 바뀌는 것을 확인했다. 삭제된 Workout의 동일 create key replay는 410이며 되살아나지 않는다. 390px 홈과 진행 그래프에서 가로 넘침이 없었고, 테스트용 D1/config와 서버는 정리했다.

마지막 QA에서 직접 입력 dialog의 Tab이 BODY로 빠지는 문제를 찾아 직접 입력/삭제 dialog 모두의 Tab·Shift+Tab 순환, 초기 초점, pending 중 disabled 제어, Escape/취소 후 초점 복귀와 추가된 항목 초점을 보완했다. 실제 Orca 브라우저 키보드 검증과 회귀 테스트 4개가 통과했다. 편집 화면의 반복 부제도 제거했다.

코디네이터가 마지막 수정까지 포함한 `pnpm test` 157/157, `pnpm typecheck`, `pnpm build`를 확인했다. 기본 테스트 명령에 `src/components`도 포함해 새 draft/초점 회귀가 빠지지 않도록 했다. 기존 로컬 개발 DB에는 추가 schema인 `0003_strength_workouts.sql`을 `--local --persist-to ./.wrangler/state`로 적용해 성공했다. 기존 측정/목표 데이터를 지우거나 소급 지급하지 않았으며 원격 리소스·배포는 하지 않았다. 이 단계 변경은 아직 커밋하지 않았다.

미래 기록이나 profile 시간대 변경 때문에 취소 localDate가 최초 지급 localDate보다 앞서 음수 과거 XP가 되는 경우는 여전히 정책 미정이다. 현재는 source/award/event를 바꾸지 않고 409로 거부하며, 날짜 이동·XP clamp·미래 입력 금지를 임의로 추가하지 않았다.

## 11. 미래 운동 기록 금지와 XP 차감일 확정

사용자가 미래 시각 운동 기록을 허용하지 않고, XP 차감은 시간대와 무관하게 원래 등록된 일에 반영하도록 결정했다. 따라서 이전의 수정일 차감·과거 그래프 보존 정책과 임시 409 예외를 대체한다. 취소되는 개별 지급의 원래 등록 localDate를 기준으로 과거 XP/레벨을 다시 계산하며, 이후 수정에서 새로 지급된 XP는 그 지급이 등록된 날짜를 사용한다. source의 수정된 날짜나 현재 profile timezone으로 취소 날짜를 다시 계산하지 않는다.

등록·수정 API와 입력 폼에서 미래 UTC instant를 거부한다. 기존 저장 기록을 조회하는 구조 검증기는 시각 제한과 분리해 과거 버전에서 허용한 기록이 조회 불능이 되지 않게 한다. 기존 ledger의 수정일 차감도 원래 지급과 연결해 집계하므로 데이터 삭제나 임의 clamp 없이 새 규칙을 적용할 수 있다. Product Concept·Roadmap·Glossary와 README의 미정 설명을 갱신했다.

실제 구현에서도 등록·수정 경계에 서버 현재 시각 검증을 추가했고, 입력 필드 변경·제출·최종 draft 구성에서 동일 제한을 검사한다. 미래 값은 초안을 보존한 채 저장 요청 없이 거부하며, 과거 값으로 고친 뒤 저장하면 기존 idempotency key를 유지한다. 기존 미래 기록의 조회·삭제는 허용해 저장 데이터를 잠그지 않는다.

새 -1 event는 현재 활성 +1 지급과 매칭한 원래 localDate로 저장한다. 집계도 동일한 매칭을 사용하므로 기존 수정일 ledger와 재지급 후 취소까지 과거 그래프가 올바르게 재계산된다. 시각/시간대 역전만을 이유로 정상 취소를 막던 임시 409 예외는 해소했고, 잘못된 ledger와 stale version 등 실제 불일치 검증은 유지한다.

검증: 도메인 56개, 입력 관련 7개와 실제 브라우저의 미래 입력 차단·과거 값 저장 검증이 통과했다. 최종 `pnpm test` 166/166, `pnpm typecheck`, `pnpm build`, `cf build`, whitespace 검사를 통과했다. 기존 데이터나 schema를 바꾸는 migration과 원격 배포는 필요하지 않았고 수행하지 않았다. 이 정책과 관련된 미정 사항은 해결됐다.
